# 移动路由卡顿调查：真实采集与活数据回放

2026-10-11；源码基线 `23639f9a8aeb87ad3a971643d49658d675d06951`。
此次修改没有重新启用路由快照，保留平台进入、返回、预测返回与滚动拉伸。

## 真机发现

用户在正式 Android App 中实际操作「计算机 → K8+ → 系统手势返回」，
随后操作频道与消息串。两轮已确认复现的 ADB/Perfetto 采集保存在本地，
原始日志、消息内容和私有环境信息不进入仓库。第三轮只有启动/动态页活动，
没有确认路由复现，不计入路由证据。

环境：Moto XT2603_1，Android SDK 37，120 Hz，1264×2780，DPR 3；
Flutter 3.47.6，engine `692136cb65`；正式 App 使用 Impeller，实验保留相同
渲染配置，但实验日志没有识别具体后端。系统无障碍语义保持开启。

确认存在两类成本，不能全部归因于详情页内容：

- **Dart/UI 工作。** 已观察到频道完整 UI 周期约 44.8 ms、消息串约
  56.3 ms。工作区数据通知原来会无条件调用根组件 `setState`、刷新根路由、
  重配移动 Navigator，以及重复写入未变化的最后访问 URI。频道及实体的
  后台变化可以触发这些工作，即使当前是内容很少的计算机详情页。
- **原生/GPU 提交等待。** 一帧 K8+ 的 raster span 为 41.8 ms，但同帧
  Dart 完整 UI 周期仅 0.915 ms，engine build 为 0.581 ms。时钟对齐后的
  Perfetto 显示，约 40.3 ms 位于 QueuePresent/queueBuffer 等待。这个帧
  不能解释成 Dart 重建耗时，也不足以证明是纹理分配或字体栅格化。

早期诊断日志按多对象批量输出，被 Android 单行限制截断；只恢复了完整的
前缀对象。因此这些数值是实际观察到的慢帧，不是完整样本分布的最大值或
验收基线。保留截断记录，不补造丢失帧。已改为单对象单行，并记录导出耗时
与丢弃数量。

## 已修改的生产路径

1. 根组件只因账号、入驻状态、服务器选择等根界面事实变化而刷新。
   普通消息、未读及缓存变化仍由业务页面消费；真正的业务导航继续发布 URI。
   最后访问 URI 仅在改变时落盘。
2. 移动 Navigator 只订阅历史、导航槽、权限及 tab 配置变化。
   活动页面继续收到数据通知；没有新增第二份导航或同步权威。
3. 公告入口/生命周期宿主放在工作区根部，避免每个详情页重新读取公告。
4. 非可见消息的后台准备等待路由空闲；进入、退出或按住预测返回期间不启动
   空闲批次。可见行和实时数据的正常渲染不等待后台准备。

借用 controller 的历史页原本就不订阅第二条工作区事件流；已核对源码，
没有以「重复 socket ingestion」作为修复理由。

## 独立 App 的活数据负载

原先仅挂载 WorkspaceView 的导航测试不足以暴露根路由、恢复与数据库成本。
fixture v4 改为启动生产 `RaftApp`，经过实际会话恢复、系统字体主题、根路由、
保留页面和后台 SQLite。每个主题使用独立的新数据库。

每次进入和返回都在转场中回放 9 个事件：消息创建/修改、任务状态修改、
另一个频道的消息、计算机状态版本、Agent 活动、Agent 创建/修改/删除。
可变服务端数据通过实际 HTTP 适配器返回；socket 事件由生产 reducer、
message ledger 和实体目录接收；Agent 修改还触发真实去抖重验。
HTTP 延迟、PNG 下载、图片解码、附件 URL 解析、已读回执与缓存写入参与运行。

测试逐次核对 10 个实际接受状态，事件丢失或重验不成立会失败；不会只依据
动画播放或 `setState` 判断成功。每个转场记录通知、请求/响应、图片请求、
缓存读/完成写入及预测返回计数。报告汇总保留这些计数。

数据来自固定公开 fixture；事件类型与生产行为对齐，但频率和网络延迟是
可重复的控制输入，并非生产服务器逐包录制。Android 返回通过原生
`flutter/backgesture` 协议回放并在途中按住；实际物理手势由前述正式 App
采集补充，协议回放不冒充人工手势验收。

## 首轮同负载比较

基线工作树保留原生产实现，仅同步同一份 v4 测试文件。基线与候选都运行：
K8+ 10 次往返、频道 3 次往返、消息串 3 次往返。
两轮各 32 个转场、288 个事件、320 个接受状态核对、16 次预测返回；
均无场景失败或未覆盖 API。正式 App 的安装/数据目录检查前后相同。
基线/候选分别完成 215/214 次缓存写入，图片请求 23/22 次；后者取决于
可见行及完成时序，不能宣称每轮图片工作量完全相等。

| 场景 | UI p90，ms | UI p99，ms | UI 最大，ms | UI 或 raster 超过 8.33 ms 的帧 |
|---|---:|---:|---:|---:|
| K8+ 详情 | 8.84 → 6.94 | 13.72 → 12.87 | 22.88 → 21.24 | 16.0% → 8.8% |
| 主页 → 频道 | 17.11 → 8.10 | 24.73 → 21.26 | 55.42 → 42.52 | 48.9% → 15.9% |
| 频道 → 消息串 | 24.11 → 3.43 | 33.54 → 25.93 | 44.51 → 35.73 | 25.7% → 11.4% |

两轮均被工具标记 **NOISY**（主机负载高于阈值），不能作为最终性能验收。
60 Hz gate 和 120 Hz 目标均未通过；比较工具还报告 K8+ 超过 16.7 ms 的
UI 帧 3 → 4、raster 帧 10 → 13。不能因为平均/分位成本改善就忽略这些尾帧。
公告在转场期间的额外读取为 16 → 0，是可直接核对的冗余工作减少。

候选的慢帧仍集中在消息行布局和语义更新；GPU 提交等待也尚未证明消除。
后续应在相同活数据负载上逐项归因，并用正式 App 物理返回采集复核。
不能用静态空白页面、关闭无障碍、移除过渡或恢复快照宣称达到门槛。

## 重用

- 日常构建的正式 App 默认关闭性能探针；启用与只读采集见
  [路由探针](route-performance-probe.md)。
- 活数据基准、隔离安装保护及同负载比较见
  [performance lab](performance-lab.md)。
- 按功能验证：根服务器选择/撤权、移动历史与数据 owner、公告单次入口、
  路由空闲准备及真实事件接受状态使用相关 widget/逻辑测试；本轮真机只覆盖
  上述三个导航场景。其他平台、其他 `nav-*` 场景不计为已验收。

最终相关 57 项 Flutter 测试、11 项探针/报告 Python 测试通过，分析器无问题，
设计系统审计没有新增强制项。普通 ARM64 release 8041 已通过保护脚本预检
并更新到手机，保留数据目录；探针关闭，APK 仅包含 arm64-v8a，AOT 中不包含
探针日志标记。构建过程中保留了一次插件注册失败：从 profile 切到 release
时 `--no-pub` 跳过了注册文件再生成。后续构建和性能工具去掉该选项，确保
不同模式正确处理 `integration_test`；没有通过修改生产依赖或卸载 App 绕过。
