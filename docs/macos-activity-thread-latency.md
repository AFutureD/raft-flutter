# macOS 动态页打开消息串的延迟调查

2026-10-11；Kevin 的问题：主页切频道很快，动态页点消息串每次约有 100–300ms 的停顿。调查基线为 `bd869aeae5fea825ccde778b28428fe86156ba22`，Flutter 3.47.6 / Dart 3.13.5。此报告定位原因与修改边界，本轮没有修改产品行为或部署 App。

## 确定的延迟来源

桌面动态页的单击路径有一段**主动等待 220ms**。这段等待发生在选中详情、读取消息串缓存和发出消息请求之前；即使消息串已经访问过，也必须经过它。这足以解释每次切换都迟迟不响应的主要现象。

`ResourceView.activateActivity`（`lib/features/resource_view.dart:3345–3364`）在存在 `onActivityCanonical` 回调且 activation detail 为 1 时启动 220ms 定时器。只有定时器到期，并且页面权限范围和导航版本仍有效，才执行 `openConversation`。重复输入会取消前一个定时器，因此快速点不同条目也会延后最后一次打开。

`WorkspaceView`（`lib/features/workspace_view.dart:1205–1220`）只在桌面宽度且动态页启用主列表/详情布局时安装这个回调。因此这不是 macOS 平台专用的节流，而是桌面动态页交互规则。窄屏直接打开完整页面，以及不提供此回调的嵌入消费者，都没有这层等待。

| 阶段 | 桌面动态页单击消息串 | 主页切频道 |
| --- | --- | --- |
| 输入组件 | 第一击立即分发 | 直接执行选择 |
| 应用交互仲裁 | 等待 220ms 区分单击/双击 | 无此定时器 |
| 选中目标、准备已缓存数据 | 220ms 之后才开始 | `selectChannel` 同步发布目标并通知显示 |
| 缓存命中 | 已缓存父消息/回复可立即显示，后台刷新 | 已有消息窗口保留，后台刷新 |
| 冷数据 | 220ms 之后才开始父消息和回复请求 | 无动态页的额外 220ms 门槛 |

输入组件 `RaftConversationCard`（`packages/raft_ui/lib/src/resource_cards.dart:161–183,251–268`）自己统计成功点击次数，第一击立即调用消费者；没有安装 `InkWell.onDoubleTap` 来叠加 Flutter 的首次点击等待。当前已确认的固定等待在应用层。

## 为什么有这个定时器

仓库既定的 [Activity 交互合同](activity-activation-contract.md) 和 [导航合同 N24](source-navigation-contract.md) 明确规定：桌面单击等待 220ms 后在动态页旁显示内容；双击取消单击，转入完整频道/消息串页面，并且只增加一次历史记录。`git blame` 指向实现这项合同的 `845adddf`。这是当时对齐固定 Web 来源的交互选择。

单击与双击还可能定位到不同回复：单击按未读/最新回复定位，双击优先提及自己的回复（`lib/features/activity_destination.dart:20–51`）。因此不能仅删除定时器而忽略定位、已读和历史语义。

## 缓存与请求复查

`WorkspaceController._openThreadIdentity`（`lib/data/workspace_controller.dart:4191–4430`）并没有再串行等待父消息之后才读回复：已知真实 thread channel 的动态行直接启动回复请求，父消息元数据独立并发获取，不走 thread-channel 解析请求。`openDesktopActivity` 也先发布目标，不等待整个网络操作完成才显示详情槽。

有效的 `_threadWindows` 命中时，父消息和回复在打开操作开始时同步恢复，`threadLoading` 为 false；关闭消息串不会删除这份内存窗口。已有测试把刷新响应永久挂起，仍能立即显示缓存内容。

缓存受账号/服务器、权限版本、消息串身份和焦点消息约束。如果新未读目标不在已接受的回复窗口中，会重新取该焦点的上下文；首次访问也需要网络。这些情况会在 220ms 之外增加等待。它们不能解释已缓存窗口仍然统一先停顿 220ms，也不应通过跳过权限栅栏或展示错误焦点来消除。

## 本轮可重复的验证

使用真实 `WorkspaceView` / `ResourceView` 的行点击和受控 HTTP transport，没有直接调用 UI 的打开回调代替点击。

- `workspace_activity_activation_test.dart`：15 项通过；三种主题，单击后 219ms 仍无详情目标、thread identity 或父消息请求，220ms 才打开；独立挂起父消息和回复请求也能重现这个边界。双击场景保留一次完整页面跳转。
- `activity_open_clears_new_test.dart`：18 项通过；主列表/详情消费者先等待，立即打开的消费者没有等待；已读徽章、请求和持久回执仍符合当前合同。
- `thread_reopen_cache_test.dart`：2 项通过；尾部/指定回复重开时，刷新永不返回也能显示父消息和回复，没有 Loading。
- `conversation_card_activation_test.dart`：5 项通过；输入层即时第一击、重复输入、键盘输入、嵌套按钮排除和重新挂载不产生输入。
- 全工程静态分析无问题；设计系统审计无增长。没有独立跑整套工程检查。

上述时间是 Flutter widget 测试的确定性时钟边界，不是 macOS Profile 的真实点击到屏幕呈现数据。没有测量当前正式 App 的网络耗时、CPU/GPU 首帧耗时或其他同步处理是否另有贡献，也没有进行原生窗口操作。不能把此结果当成整版 120fps 验收。

## 建议的修改与验收

优先让**第一次单击立即显示消息串预览，第二次激活升级为完整页面**。把双击识别从“等完才显示”改为“显示后再升级”；双击仲裁不再阻塞可见反馈。热缓存应在下一可用帧显示；冷窗口应立刻显示真实目标的标题并并发加载数据，不能保留旧目标造成点击无效的观感。

实施时需要一并更新 N24 中“单击必须等 220ms、双击前没有任何预览”的具体时序合同。保留双击的最终目标与焦点、一次完整页面 PUSH，以及权限和迟到响应栅栏：

1. 保留首击的不可变行数据，避免立即标记已读/重建行之后，第二击丢失原来的未读定位；按原行数据计算双击目标。
2. 预览选择和完整页升级按同一次激活事务管理，检查同一行、权限范围、导航版本；旧父消息/回复响应不能覆盖新目标。已有内容槽的替换与完整页 PUSH 需分别处理。
3. 已读操作须合并或明确提交时机，不能产生重复写入；同时保持第一帧已读徽章与列表稳定。选不同条目不再互相取消可见打开，只退役旧请求的接受资格。
4. 验收真实鼠标首击、热缓存且刷新挂起、冷父消息/回复分别挂起、快速跨行点击、双击、键盘和无障碍激活、Back/Close，以及账号/服务器/权限变化后迟到响应。焦点坐标和首次已显示行不能抖动。

修改后应在同源码的 macOS Profile 上记录：输入事件、目标发布、缓存/请求开始、首个正确详情帧，比较冷/热两组。原生 UI 操作继续遵循后台 Computer Use 绑定约束。

把定时器缩短到 100ms 仍会留下固定延迟和双击竞态；增加 CPU 性能提示不能消除主动等待。首要工作应是这个交互时序，而后才是剩余网络和首帧处理。
